### Condición necesaria para afirmar “adherence to a habit target”

Atlas necesita una expectativa explícita, propiedad del usuario y efectiva por fecha: para cada hábito fijo, qué días de semana espera registrarlo y desde qué fecha rige cada versión. Solo entonces puede calcular:

- numerador: habit-days esperados transcurridos con `habit_logs.done = true`;
- denominador: habit-days esperados transcurridos según la versión de schedule vigente en cada fecha.

Mostrar los cuatro hábitos todos los días no constituye intención diaria. Tampoco la cantidad de litros registrada constituye un target de hidratación.

## 3. Continuidad del recorrido actual

| Flujo | Evidencia de continuidad | Dónde deja de producir valor adicional |
|---|---|---|
| Onboarding | Guarda `goal/pace/equipment`; Finish sincroniza, Skip no | No expresa intención sobre hábitos |
| Today | Plan de hoy + check-in + Coach + hábitos + semana | Los hábitos aparecen todos los días sin distinguir “objetivo de hoy” de “registro opcional” |
| Plan/guided plan | Brief editable, propuesta Gemini/fallback, revisión y guardado explícito | Contexto persistido y contexto de mejora no están completamente unificados |
| Routines | Catálogo/CRUD/Coach draft con ownership | No es el cuello de botella del loop de hábitos |
| Session/workout | Sets reales, skip/hold, media, cierre | Funciona; issues históricos #18 ya están resueltos |
| Post-workout | Feedback explícito, opcional y persistido | No alimenta todas las propuestas futuras; oportunidad posterior |
| Habits | Acción actual → evidencia actual/histórica | Falta la intención explícita; Atlas observa pero no puede evaluar contra lo que el usuario quiso hacer |
| Progress | Evidencia → feedback de sesiones, fuerza, bienestar hoy y actividad de hábitos | La actividad de hábitos no puede convertirse honestamente en cumplimiento objetivo |
| Profile/Settings | Contexto Coach editable y entrada a hábitos | No existe configuración de intención de hábitos |
| Coach | Contexto explícito → preview → confirmación → sesión adaptada | No aprende; contextos entre flows no están consolidados |

El corte dominante del loop es:

```text
acción de hábito → evidencia registrada → actividad observada
                    ↑
             falta intención explícita
```

Sin intención no hay feedback contra un target ni una siguiente acción basada en cumplimiento.

## 4. Problemas candidatos

### Candidato A — Atlas observa hábitos pero no conoce la intención del usuario

**USER PROBLEM**

El usuario puede registrar y revisar hábitos, pero no puede decir qué días pretende hacer cada uno; por eso Atlas no distingue actividad extra, cumplimiento ni ausencia relevante.

**CURRENT EVIDENCE**

`HABIT_KEYS` fijo, `habit_logs`, read path v0.9, ausencia total de schedule/targets.

**WHY THIS PROBLEM EXISTS NOW**

v0.9 resolvió primero el prerequisito correcto: historia observable y honesta.

**MISSING CAPABILITY**

Schedule semanal por hábito, versionado y efectivo por fecha; cálculo de expected habit-days.

**WHAT BECOMES POSSIBLE IF SOLVED**

Cumplimiento real contra target, “objetivo de hoy”, feedback histórico y futura discovery de reminders sin inferir intención.

**DEPENDENCIES**

Migración; servicios de versionado; extensión aditiva del read path; UI de configuración.

**RISKS**

Reescribir expectativas pasadas, confundir frecuencia con cantidad, penalizar días futuros, mezclar actividad con cumplimiento.

**WHAT IT DOES NOT REQUIRE**

Hábitos custom, IA, reminders, streaks, backdating, Liftoff.

### Candidato B — El contexto explícito de Coach/Plan cambia según el flujo

**USER PROBLEM**

El usuario configura preferencias, pero algunos flujos solo las usan como prefill cliente y `improve-plan` hardcodea experiencia/duración.

**CURRENT EVIDENCE**

`user_preferences`, `useGuidedPlan`, generation body-only, hardcodes en `training-plan-improvement.ts`.

**WHY THIS PROBLEM EXISTS NOW**

Los flows crecieron por capas y no comparten un ensamblador canónico de contexto.

**MISSING CAPABILITY**

Context assembler server-side con precedencia explícita entre perfil, plan y override del usuario.

**WHAT BECOMES POSSIBLE IF SOLVED**

Propuestas consistentes entre guided plan, routine coach e improve-plan.

**DEPENDENCIES**

Decidir si experiencia/duración se persisten, y qué fuente gana en cada flow.

**RISKS**

Scope cross-domain, cambios de contrato y riesgo de describir preferencias como aprendizaje.

**WHAT IT DOES NOT REQUIRE**

Historial de hábitos, progreso nuevo, mutación automática del plan.

### Candidato C — Progreso conserva dos promesas visibles incorrectas

**USER PROBLEM**

El usuario ve dos botones que no actúan y “Volumen no disponible” cuando el dato existe en otro resumen.

**CURRENT EVIDENCE**

`ProgressHeader.tsx`, `RecentSessionsCard.tsx`, `strength-progress.ts`.

**WHY THIS PROBLEM EXISTS NOW**

La convergencia visual precedió al contrato completo de esas affordances.

**MISSING CAPABILITY**

Eliminar/deshabilitar acciones sin contrato y transportar volumen por sesión.

**WHAT BECOMES POSSIBLE IF SOLVED**

Una pantalla más honesta y consistente.

**DEPENDENCIES**

Alinear `progress-summary` con `strength-progress` por workout.

**RISKS**

Bajos; principalmente compatibilidad de DTO.

**WHAT IT DOES NOT REQUIRE**

Nueva entidad, IA ni release temática.

### Candidato D — Datos de feedback e historia no cierran un loop futuro de recomendación

**USER PROBLEM**

El usuario registra esfuerzo, molestias, sesiones, fuerza y hábitos, pero la mayoría de propuestas futuras no consume esas señales.

**CURRENT EVIDENCE**

Datos persistidos en varias tablas; Coach preview solo usa rutina/check-in/texto; guided plan usa brief explícito.

**WHY THIS PROBLEM EXISTS NOW**

La captura y la ejecución maduraron antes que un contrato de contexto multi-señal.

**MISSING CAPABILITY**

Resumen determinístico de contexto, límites de autoridad y reglas de relevancia por flow.

**WHAT BECOMES POSSIBLE IF SOLVED**

Recomendaciones más contextuales sin afirmar aprendizaje.

**DEPENDENCIES**

Decisiones de producto sobre precedencia, ventanas y explicación; alta superficie AI/QA.

**RISKS**

Sobreinterpretación, privacidad, prompts grandes, recomendaciones difíciles de probar.

**WHAT IT DOES NOT REQUIRE**

Mutación silenciosa ni ML.

## 5. Comparación de tesis

| Dimensión | A — intención de hábitos | B — contexto Coach/Plan | C — honestidad Progress | D — feedback contextual |
|---|---|---|---|---|
| Continuidad | Extensión directa del loop v0.9 | Corrige fragmentación v0.7/v0.8 | Limpieza puntual | Extiende varios loops a la vez |
| Valor directo | El usuario declara intención y recibe feedback contra ella | Mejores propuestas, impacto menos visible | Confianza y claridad | Potencial alto, causalidad difícil de explicar |
| Honestidad | Habilita por primera vez un denominador legítimo | Exige precedencia explícita | Corrige dos defectos | Alto riesgo de sobreinterpretar |
| Leverage arquitectónico | Reusa logs, Córdoba, activity windows y `Metric<T>` | Reusa preferencias/plan | Reusa summaries | Requiere ensamblador nuevo y AI boundaries amplios |
| Dependencias | Migración acotada + UI/API | Nuevas decisiones de perfil | Muy pocas | Muchas decisiones cross-domain |
| Tamaño | Release mediana coherente | Mediana/grande y transversal | Demasiado pequeña como tesis | Grande |
| Riesgo de migración | Moderado, sin backfill | Bajo si no persiste campos nuevos; incierto si sí | Ninguno o DTO additive | Posible schema/snapshots |
| Compatibilidad | Aditiva; actividad v0.9 preservada | Riesgo de cambiar propuestas existentes | Aditiva | Riesgo alto en Coach/Plan |
| Dependencia AI | Ninguna | Parcial | Ninguna | Alta aunque haya fallback |
| QA | Timezone/versionado/metrics | Matriz cross-flow | Acotada | Muy amplia |
| Opcionalidad futura | Reminders, honest adherence, later Liftoff discovery | Mejor personalización explícita | Poca | Amplia pero prematura |

### Selección

**Tesis v0.10.0:** *Atlas v0.10 permite que el usuario defina en qué días espera realizar cada hábito del catálogo, persiste esa intención con vigencia histórica y la compara con registros reales para mostrar cumplimiento objetivo verificable, sin inferir metas, cantidades ni conducta en días no programados.*

Es la única tesis que completa `intención → acción → evidencia → feedback` con una fuente canónica nueva y sin depender de IA. C es MUST complementario por honestidad, pero no tesis. B y D quedan para una discovery posterior.

## 6. Product contract

### User problem

Atlas conoce lo que ocurrió, pero no qué esperaba el usuario que ocurriera. La ausencia de expectativa impide feedback de cumplimiento.

### Target user behavior

1. El usuario abre Hábitos.
2. Para uno o más hábitos del catálogo fijo, selecciona días de semana objetivo.
3. Atlas muestra qué hábitos están programados hoy sin ocultar los demás.
4. El usuario registra como hoy.
5. Hábitos y Progreso muestran cumplimiento solo sobre días objetivo transcurridos.
6. El usuario puede cambiar o desactivar un schedule sin reescribir días anteriores.

### Explicit user actions

- `Configurar días` por hábito.
- `Guardar cambios` con resumen de vigencia “desde hoy en Córdoba”.
- `Desactivar objetivo` con confirmación; conserva historia.
- Toggle/amount de hoy, sin cambios al write path existente.

### Domain entities

`HabitTargetSchedule`

- `id`
- `userId`
- `habitKey`
- `effectiveFrom` (Córdoba `YYYY-MM-DD`, inclusive)
- `effectiveTo` (Córdoba `YYYY-MM-DD`, inclusive, nullable)
- `version` (integer monotónico por schedule, inicia en `1`)
- `createdAt`, `updatedAt`

`HabitTargetDay`

- `scheduleId`
- `dayOfWeek` (`0=Sunday … 6=Saturday`, igual que training plans)

No se crea `HabitDefinition`; el catálogo sigue siendo `HABIT_KEYS`.

### Ownership and source of truth

- El usuario autenticado es dueño de todos sus schedules.
- `types/habit.ts` sigue siendo fuente de identidad del catálogo.
- DB (`habit_target_schedules` + `habit_target_days`) es fuente canónica de intención histórica.
- `habit_logs` sigue siendo fuente canónica de acción observada.
- Nunca se deriva intención desde UI diaria, logs, streaks, Coach o defaults.

### Lifecycle

- Un hábito puede no tener schedule activo; eso no elimina versiones históricas.
- Crear: primera versión efectiva desde la fecha Córdoba actual.
- Actualizar: cierra la versión activa en el día anterior e inserta una nueva versión desde hoy, dentro de una transacción.
- Si ya existe una versión creada hoy, un PUT posterior actualiza días y aumenta `version` en esa misma fila en vez de crear otra; no altera fechas anteriores.
- Desactivar una versión iniciada antes de hoy la cierra en el día anterior y aumenta `version`; nunca borra historia.
- Desactivar una versión creada hoy elimina transaccionalmente solo esa versión y sus días: todavía no representa historia anterior a hoy y cancelar hoy hace que hoy vuelva a no esperado. Un log de hoy se conserva como actividad extra. Este es el único hard delete permitido.
- Repetir el mismo PUT/DELETE es idempotente por estado.
- No se permiten versiones superpuestas ni schedules con cero días.

### Mutation authority

Solo una acción explícita del usuario vía UI/API puede crear, actualizar o desactivar el schedule. Coach, crons, migrations y reads no tienen autoridad de mutación.

### Timezone/date semantics

- `effectiveFrom/effectiveTo`, expected dates y “hoy” usan Córdoba.
- Un cambio confirmado el 2026-09-28 es efectivo desde `2026-09-28` y nunca modifica `<= 2026-09-27`.
- Días futuros pueden ser esperados en el schedule pero nunca entran al denominador hasta transcurrir.
- Una fecha sin schedule vigente no es esperada y no es incumplimiento.

### Historical compatibility and backfill

- Logs previos al primer schedule permanecen actividad observada y quedan fuera de target adherence.
- No se infiere schedule retroactivo y no hay backfill de expectativas.
- Los datos v0.9 y su endpoint permanecen byte-compatible.

### Empty states

- Sin schedules: “Configurá los días que querés proponerte; tu actividad anterior sigue visible.”
- Schedule configurado pero sin día objetivo transcurrido en ventana: “Todavía no transcurrió un día objetivo en este período.”
- Días objetivo transcurridos sin logs: numerador `0`, denominador real `>0`; esto sí es un resultado, no ausencia de datos.
- La configuración actual y el resultado de la ventana son ejes distintos: desactivar hoy no oculta un `N/M` histórico dentro de la ventana seleccionada.

### Error states

- 401 sesión vencida.
- 400 clave/días/body inválidos.
- 404 hábito no perteneciente al catálogo cerrado.
- 409 versión esperada obsoleta si el cliente intenta guardar sobre estado cambiado.
- 500/503 nunca se presentan como cero cumplimiento.

### Provenance

- Schedule/días seleccionados: `user_input`.
- Numerador, denominador, porcentaje y estados diarios derivados: `atlas_computed`.
- Logs/toggles: `user_input`.

### Scope clarification: quantitative habits

Hidratación conserva `amount` como registro. v0.10 no configura litros objetivo y no decide cumplimiento por cantidad. El target es exclusivamente “registrar este hábito en estos días”; `done=true` es el cumplimiento de ese habit-day esperado.

## 7. Data semantics and metrics

### Expected habit-day

Para una fecha Córdoba `D` y hábito `H`, existe expectativa si:

1. hay una versión de schedule de `(user,H)` donde `effectiveFrom <= D <= effectiveTo`, tratando `NULL` como sin fin; y
2. `sundayFirstWeekday(D)` pertenece a `habit_target_days` de esa versión.

`DayOfWeek` usa explícitamente `0=Sunday … 6=Saturday`, igual que training plans. El dominio debe exportar un helper Córdoba Sunday-first desde `lib/time/cordoba.ts`; **no** puede usar `localDateWeekdayIndex`, porque ese helper existente es Monday-first (`0=Monday … 6=Sunday`).

### Metric contract

| Métrica | Numerador | Denominador | Ventana | Fuente | Minimum required data | Significado | NO significa |
|---|---|---|---|---|---|---|---|
| `expectedHabitDays` | n/a | count de habit-days esperados transcurridos | week/30d/90d Córdoba | schedules versionados | 1 habit-day esperado | oportunidades que el usuario declaró | días donde Atlas supone que debía actuar |
| `completedExpectedHabitDays` | expected habit-days con log `done=true` | `expectedHabitDays` | misma | schedules + `habit_logs` | denominador >0 | objetivos diarios registrados | calidad, esfuerzo o cantidad |
| `habitTargetAdherence` | `completedExpectedHabitDays` | `expectedHabitDays` | misma | puro, `atlas_computed` | denominador >0 | cumplimiento contra intención explícita | actividad total ni score de fitness |
| `habitTargetAdherencePercent` | igual | igual | misma | puro; `round(100*n/d)` | denominador >0 | representación del ratio anterior | probabilidad, readiness o recompensa |
| `perHabitTargetAdherence` | completados esperados de H | esperados transcurridos de H | misma | puro | denominador de H >0 | cumplimiento de un hábito | comparación entre hábitos |
| `extraRecordedHabitDays` | registros `done=true` sin expectativa para H/D | n/a | misma | `habit_logs` + schedules | 1 extra | actividad adicional observada | cumplimiento o incumplimiento |

La UI debe mostrar siempre el par `N de M días objetivo`; el porcentaje puede acompañarlo, nunca reemplazarlo. Ningún agregado suma entrenamiento y hábitos.

### Daily state union

```ts
type HabitTargetDayState =
  | 'future_expected'
  | 'expected_completed'
  | 'expected_unrecorded'
  | 'extra_recorded'
  | 'not_expected';
```

`expected_unrecorded` es legítimo porque la expectativa existe. No se usa “fallaste”; el copy será “sin registro en un día objetivo”.

La respuesta separa dos estados:

- `configurationState`: `not_configured | partially_configured | configured`, según cuántos de los cuatro hábitos tienen target activo hoy;
- `metricState`: `no_expected_days | result`, según el denominador de la ventana, con el mismo `metricState` por hábito.

Si un target terminó pero aporta días esperados transcurridos a la ventana, `configurationState` puede ser `not_configured` mientras `metricState` es `result`; la UI muestra el `N/M` histórico. Un hábito configurado sin oportunidad transcurrida tiene `metricState=no_expected_days`. Un resultado parcial nunca se oculta porque otros hábitos estén sin configurar. El porcentaje existe solo para un estado `result` con denominador mayor que cero.

## 9. Architecture

### Database

Nueva migración, después de `0022_routine_plan_scope`:

```text
habit_target_schedules
  id INTEGER PRIMARY KEY AUTOINCREMENT
  user_id INTEGER NOT NULL FK users(id)
  habit_key TEXT NOT NULL CHECK catalog
  effective_from TEXT NOT NULL
  effective_to TEXT NULL
  version INTEGER NOT NULL DEFAULT 1 CHECK version >= 1
  created_at INTEGER NOT NULL
  updated_at INTEGER NOT NULL

habit_target_days
  schedule_id INTEGER NOT NULL FK habit_target_schedules(id) ON DELETE CASCADE
  day_of_week INTEGER NOT NULL CHECK 0..6
  PRIMARY KEY (schedule_id, day_of_week)
```

Indexes/constraints:

- unique partial active schedule `(user_id, habit_key) WHERE effective_to IS NULL`;
- unique `(user_id, habit_key, effective_from)`;
- range index `(user_id, effective_from, effective_to)`;
- check `effective_to IS NULL OR effective_to >= effective_from`;
- `version` se incrementa atómicamente con compare-and-swap en cada PUT/DELETE que modifica una fila;
- schedule days PK evita duplicados.

SQLite no puede expresar por sí solo “no overlap” entre intervalos. El service lo garantiza en transacción y los tests de repositorio prueban carrera/conflicto. La partial unique impide dos versiones activas.

Migration behavior:

- crea tablas vacías; cero backfill;
- no toca `habit_logs`;
- rollback manual puede eliminar solo las dos tablas nuevas, perdiendo configuración de targets pero no actividad; antes de rollback productivo se exportan esas tablas;
- deployment order: migrate → deploy app → smoke.

### Domain

Nuevos tipos en `types/habit-target.ts` y `types/habit-adherence.ts`.

Funciones puras:

```ts
resolveExpectedHabitDays(input): ExpectedHabitDay[]
computeHabitTargetAdherence(input): HabitTargetAdherenceWindow
```

Invariantes:

- clave conocida;
- entre 1 y 7 valores weekday distintos, cada uno en `0..6` Sunday-first;
- intervalos no superpuestos;
- dates Córdoba canónicas;
- matching de weekday mediante el nuevo helper Sunday-first, nunca mediante `localDateWeekdayIndex` Monday-first;
- future excluded;
- logs previos a intención no se vuelven esperados;
- `done=true` único signal de completion;
- counts antes que porcentaje.

### Services

- `listCurrentHabitTargets(userId, now?)`.
- `putHabitTarget(userId, habitKey, input, now?)`.
- `deactivateHabitTarget(userId, habitKey, expectedToken, now?)`.
- `loadHabitTargetVersionsInWindow(userId, start, end)` en una query acotada, más días en una segunda query o join único.
- `getHabitTargetAdherenceForUser(userId, period, now?)` combina schedules y el loader existente de logs.

Todas las mutaciones usan transacción. El token de concurrencia es el par `{ targetId, version }`: `targetId` no se reutiliza por `AUTOINCREMENT` y `version` es el entero monotónico de esa fila. El write usa compare-and-swap (`WHERE id=? AND version=?`, incrementando `version`); cero filas afectadas → `409 CONFLICT`. Los timestamps no se usan como token de concurrencia y una nueva versión histórica nunca puede aceptar el token de la anterior. Si DELETE recibe el token de un target que ya está ausente y no existe otro activo, devuelve el estado ausente idempotente; si existe otro target/token activo, devuelve `409`. Repetir la misma intención sobre el mismo estado devuelve el target existente.

### API

| Method | Endpoint | Request | Success | Errors |
|---|---|---|---|---|
| GET | `/api/habit-targets` | — | current targets for 4-key catalog | 401 |
| PUT | `/api/habit-targets/[habitKey]` | `{ weekdays: DayOfWeek[], expectedTargetId: number|null, expectedVersion: number|null }` | 200 update / 201 create | 400/401/404/409 |
| DELETE | `/api/habit-targets/[habitKey]` | `{ expectedTargetId: number, expectedVersion: number }` | 200 `{ activeTarget:null }` | 400/401/404/409 |
| GET | `/api/stats/habit-adherence?period=week|month|quarter` | query | typed adherence window | 400/401 |

Routes siguen `validate → auth → service → typed response → handleApiError`. `userId` solo proviene de sesión.

Errores agregan a la unión tipada solo si el código existente no alcanza. Preferencia:

- `VALIDATION`, `NOT_FOUND`, `CONFLICT`, `UNAUTHORIZED` existentes;
- no crear códigos específicos redundantes.

### Client

- `lib/api/habit-targets.ts`: parser total y errores tipados.
- `lib/api/habit-adherence.ts`: parser total, rechaza claves/días/ratios inválidos.
- `hooks/useHabitTargets.ts`: load/save/deactivate, estado por hábito, refetch tras mutation.
- `hooks/useHabitAdherence.ts`: cache por period, abort de request obsoleto.

Después de guardar/desactivar:

1. refetch targets;
2. refetch adherence;
3. el estado diario de hábitos se conserva; no optimistic rewrite de métricas históricas.

### UI

**Hábitos**

- sección `Mis días objetivo` con los cuatro hábitos fijos;
- selector accesible de lunes a domingo;
- resumen y confirmación de vigencia;
- desactivar conserva historia;
- history strip distingue expected-completed, expected-unrecorded, extra-recorded, not-expected, future.

**Today/HabitsScreen**

- cada fila indica `Objetivo de hoy` cuando corresponde;
- hábitos no esperados siguen registrables;
- no reordena ni oculta hábitos por default.

**Progress**

- nueva `HabitTargetAdherenceCard` separada de `HabitActivityCard`;
- la card de actividad v0.9 permanece observacional;
- target card tiene loading/error más `configurationState` y `metricState` independientes; un target inactivo no oculta un resultado histórico;
- `N de M días objetivo` + porcentaje derivado + provenance.

**Defectos acotados de honestidad**

- retirar los dos botones inertes del header; no implementar notificaciones/share dentro de esta release;
- propagar `totalVolumeKg` por workout a `ProgressSessionSummary` y mostrarlo cuando exista, manteniendo unavailable solo si realmente no hay sets elegibles.

Estos fixes son MUST de calidad porque la wave toca Progreso, pero no alteran la tesis ni abren sus features.

## 10. MUST / SHOULD / DEFER / EXCLUDE

### MUST

- Schedule semanal por hábito fijo, versionado por vigencia Córdoba.
- Create/update/deactivate explícitos, con optimistic conflict y preservación histórica.
- Cálculo puro de adherence sobre expected elapsed habit-days.
- API/clients/hooks tipados.
- Configuración de días en Hábitos.
- Señal “Objetivo de hoy” sin impedir registros extra.
- Read-back de cumplimiento en Hábitos y Progreso, separado de actividad v0.9.
- Sin backfill; logs previos siguen solo observacionales.
- Eliminar botones inertes de Progress.
- Mostrar volumen real por sesión cuando existe.
- Migración, compatibilidad, tests unit/service/API/component/E2E.

### SHOULD

- CTA desde la card de adherence de Progreso a configuración.
- Resumen por hábito ordenado por catálogo.
- Copy explicativo al cambiar schedule el mismo día.

La release sigue siendo valiosa si todos los SHOULD se eliminan.

### DEFER

- Hábitos creados/renombrados/reordenados por usuario.
- Targets cuantitativos (litros, minutos, pasos).
- Reminders, quiet hours, push/email/Telegram habit nudges.
- Backdating/corrección histórica.
- Hábitos dentro del streak existente.
- Coach/Plan consumiendo activity o adherence.
- Context assembler de preferencias/plan/historia.
- Eliminar hardcodes de improve-plan.
- Bienestar histórico en Progress.
- DB tooling residual y branch protection.

### EXCLUDE

- Quests, missions, XP, levels, badges, rewards, gamification y Liftoff parity.
- Composite habit+training scores.
- Inferir targets desde registros pasados.
- Mutación silenciosa por AI/cron.
- Release/version bump/main/tag en la implementación de features.

## 15. Risks and stop conditions

| Risk | Mitigation |
|---|---|
| Retroactive denominator rewrite | versioned effective intervals; no backfill; past dates immutable |
| Same-day edits create multiple versions | update today’s version in-place; unique user/habit/effective date |
| Concurrent schedules overlap | transaction + active partial unique + negative race tests |
| “Daily display = daily target” regression | target only from DB schedule; explicit `not_configured` |
| Hydration amount misread as target | quantitative targets explicitly excluded |
| Future dates count as failures | future excluded from denominator and rendered separately |
| Activity and adherence conflated | separate types, endpoints and Progress cards |
| Percent hides counts | UI always renders N/M; percentage secondary |
| Schedule deactivation deletes history | older versions end yesterday; only a version created today may be cancelled/deleted, because it has no prior target history; logs remain |
| Scope expands to reminders/AI/gamification | DEFER/EXCLUDE gates and diff review |
| D/E writers collide | separate paths/worktrees; Progress copy owned only by E |
| Current baseline moves | downstream agent stops for Architecture revalidation |

Global stop conditions:

- implementation requires custom habit definitions to make MUST coherent;
- any migration would backfill intention from historical logs;
- no-overlap cannot be guaranteed;
- the denominator would include future, unconfigured or inferred days;
- existing activity endpoint must be broken or relabeled;
- a MUST depends on AI/reminders/Liftoff;
- a new product decision outside this document becomes necessary.
