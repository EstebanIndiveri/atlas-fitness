## 5. Current user-loop analysis

```text
contexto/intención explícita
  → plan semanal/rutina
  → sesión guiada
  → sets persistidos + feedback
  → Progress agregado / cierre efímero
  → [corte: el próximo encuentro con el ejercicio no recupera esa memoria]
  → próxima decisión de peso/reps
```

Atlas ya responde “qué toca hoy” y conserva la acción. El corte dominante está entre evidencia histórica y próxima acción: cuando vuelve el mismo ejercicio, el player ofrece targets del template, inputs vacíos y una nota local vacía. La última ejecución y la nota que el usuario quiso conservar no vuelven al punto de decisión.

La pantalla de cierre agrega valor inmediato (duración, sets, volumen, comparación), pero ese feedback desaparece al volver a Today. Progress agrega por workout; no responde “¿qué hice la última vez en este ejercicio?”.

## 7. Progress / progression analysis

### Current visible metrics

| Métrica | Source | Fórmula/ventana | Significa | No significa |
|---|---|---|---|---|
| Completed sessions | completed, non-deleted workouts | count por `startedAt` dentro de week/30d/90d | sesiones cerradas iniciadas en ventana | adherencia a plan |
| Duration | workout timestamps | `round((ended-started)/60s)` | duración registrada | tiempo activo real |
| Session volume | eligible sets | `Σ(weightKg × reps)` exacto decimal | volumen cargado según inputs | tonelaje fisiológico comparable entre ejercicios |
| Strength chart | completed workouts/sets | volumen por sesión, ventana por `endedAt` | cambio de volumen total registrado | fuerza individual, e1RM o causalidad |
| Trend label | first vs last volume | decimal exact compare | dirección del volumen agregado | progresión de fuerza |
| “Punto de partida” | exactamente un point | presentation state | primer punto visible | baseline clínico o PR |

### Underused/unsafe paths

- `getExerciseHistory` devuelve sets raw pero no se consume y no limita/pagina.
- `getPersonalRecords` implementa ADR-001 (max weight, tie recent) pero incluye workouts abiertos y no filtra `completed`.
- el logger legado consulta PRs y marca un set igual al máximo como PR antes de cerrar el workout;
- el cierre compara contra el workout anterior por `startedAt`, sin exigir que estuviera cerrado, y calcula delta con `parseFloat`;
- la UI moderna no muestra historia por ejercicio.

### PR/e1RM gate

v0.11 **no expande PR ni introduce e1RM**. Aunque ADR-001 define el PR legado como máximo `weight_kg`, faltan verdades para convertirlo en una tesis de progresión:

- warm-up y working sets son indistinguibles;
- peso corporal, carga adicional, asistencia y carga total no tienen `load mode`;
- ejercicios unilaterales no declaran si el peso es por lado o total;
- el catálogo incluye dominadas/fondos y ejercicios unilaterales;
- no existe RIR/RPE por set;
- e1RM no tiene fórmula aprobada.

Decisión para esta release: los pesos/reps previos se muestran **verbatim como registros**, únicamente para el mismo `exerciseId`; no se comparan entre ejercicios ni se etiquetan como progreso. PR categories nuevas: ninguna. e1RM: inexistente. Plateau: inexistente. Recomendación de carga: inexistente.

El PR legado sigue siendo max weight/tie recent por compatibilidad, pero su hardening es mantenimiento separado y no se convierte en promesa nueva. Si se toca durante implementación para compartir queries, deberá excluir workouts abiertos, sets incompletos/borrados y usar `endedAt`; no podrá cambiar copy o categoría sin nueva aprobación.

## 8. Post-workout feedback analysis

Persistido por workout:

- `effort` entero 1–10 (`user_input`);
- `sensation` `great|good|neutral|hard|bad`;
- hasta cinco discomfort entries `{area,intensity}`;
- nota opcional hasta 500;
- un row por workout, upsert permitido;
- solo para workout propio, no borrado y cerrado.

Read-back actual: GET individual por workout, sin consumidor UI posterior. No afecta Coach preview, guided plan, improve-plan, weekly strategy, Today ni Progress. Es funcionalmente write-only después de guardar.

El copy “Atlas usa este feedback para calibrar la recuperación y tus próximas cargas” excede la verdad actual. v0.11 MUST lo reemplaza por copy de persistencia sin promesa causal: “Guardamos este feedback como parte de esta sesión. No cambia tu plan ni recomienda cargas automáticamente.”

La estructura es suficiente para mostrar historial descriptivo en el futuro, pero no para diagnosticar recovery/readiness ni atribuir molestias a un ejercicio. v0.11 no consume feedback para automatización.

## 11. Habits, Today, return loop, Profile

Habits post-v0.10 has a complete explicit loop; reminders, review, streak integration and Coach context remain legitimate opportunities but are not the strongest next gap.

Today answers plan/check-in/habits, but the return loop after a workout only exposes aggregate week/streak. When the scheduled exercise recurs, Atlas does not surface what the user did or wrote last time.

## 13. Candidate product problems

### Candidate A — The user returns to an exercise without the memory they explicitly created

**USER PROBLEM:** During guided training the user can type an exercise note and logs exact sets, but the note disappears and the previous sets are absent when the exercise returns.

**CURRENT EVIDENCE:** local `noteText`; existing persisted `workout_sets`; unused history endpoint; player inputs start without prior context.

**WHY NOW / AFTER v0.10:** execution, plan and habit intention loops are mature; training evidence is the largest ready dataset whose next action remains disconnected.

**MISSING CAPABILITY:** owned per-workout/per-exercise note plus bounded read model for last completed sets and last completed note.

**BECOMES POSSIBLE:** deliberate next-session decisions, continuity across devices/reloads and later richer history without invented scoring.

**EXISTING DATA:** workouts, sets, exercises, queue, timestamps.

**NEW DOMAIN TRUTH:** explicit exercise-session note only.

**DEPENDENCIES:** additive migration, service/API/client/UI.

**AI NEED:** none.

**RISKS:** note lifecycle, stale writes, confusing old note/date, exposing deleted/foreign history.

**DOES NOT REQUIRE:** PR, e1RM, recommended load, RPE by set, warm-ups, substitutions, gamification.

**LIFTOFF PATTERNS:** persistent notes ADOPT; history/feedback ADAPT.

### Candidate B — The user records strength work but Atlas cannot honestly call it exercise progression

**USER PROBLEM:** Raw sets and a legacy max-weight PR exist, but there is no trustworthy per-exercise progression surface.

**CURRENT EVIDENCE:** stats endpoints, close comparison, aggregate volume chart, catalog with bodyweight/unilateral exercises and no load taxonomy.

**WHY NOW:** data volume is sufficient, but semantics lag.

**MISSING CAPABILITY:** load mode, warm-up/working classification or a deliberately narrow record contract.

**BECOMES POSSIBLE:** PRs/e1RM/trends if product semantics are approved.

**EXISTING DATA:** reps, positive `weightKg`, exercise ID, completed sessions.

**NEW DOMAIN TRUTH:** substantial if records are to mean performance rather than “max entered number”.

**MIGRATION:** likely for load tracking mode/set type.

**AI NEED:** none.

**RISKS:** false progress, assisted inversion, unilateral ambiguity, historical reinterpretation.

**DOES NOT REQUIRE:** social/gamification.

**LIFTOFF:** PR/e1RM DEFER until semantics.

### Candidate C — The user gives post-workout context that Atlas never returns or uses

**USER PROBLEM:** Effort, sensation and discomfort are submitted then disappear; current copy promises recovery/load effects that do not occur.

**CURRENT EVIDENCE:** feedback table/API and zero consumers.

**WHY NOW:** capture exists; authority does not.

**MISSING CAPABILITY:** honest read-back first; any future deterministic influence needs separate rules.

**BECOMES POSSIBLE:** session reflection and later confirmed adaptation.

**EXISTING DATA:** structured workout-level feedback.

**NEW DOMAIN TRUTH:** none for read-back; major rules for automation.

**MIGRATION:** none for read-back.

**AI NEED:** none for read-back; optional later.

**RISKS:** health inference and misattribution to exercises.

**DOES NOT REQUIRE:** readiness score.

**LIFTOFF:** RPE ADAPT only at workout level already present.

### Candidate D — Explicit Coach context is inconsistent across planning flows

**USER PROBLEM:** Saved preferences prefill one flow, while routine coach and improve-plan use separate defaults/hardcodes.

**CURRENT EVIDENCE:** field matrix; improve-plan hardcodes level/session length.

**WHY NOW:** planning flows accumulated independently.

**MISSING CAPABILITY:** server-side context assembler with precedence and provenance.

**BECOMES POSSIBLE:** coherent proposals without “learning” language.

**EXISTING DATA:** preferences, active plan, explicit request.

**NEW DOMAIN TRUTH:** whether experience/duration belong to profile, plan or per-request.

**MIGRATION:** possible.

**AI NEED:** feature must remain deterministic/fallback-safe.

**RISKS:** cross-domain scope and silent behavior changes.

**DOES NOT REQUIRE:** workout history or habit adherence.

**LIFTOFF:** no decisive pattern.

## 14. Candidate comparison

| Tradeoff | A — exercise memory | B — progression | C — feedback reuse | D — Coach context |
|---|---|---|---|---|
| Product continuity | Directly joins execution to next execution | Strong but semantics incomplete | Joins close to reflection | Repairs planning consistency |
| Direct/frequent value | At every repeated exercise | High if honest | At/after workouts | Indirect via proposals |
| Existing-loop closure | Strongest | Strong | Medium unless automation added | Medium |
| Data readiness | Sets ready; note entity small | Raw data ready, meaning not | Data ready | Data ready, ownership decisions missing |
| Semantic honesty | High: declared note + raw sets | Low until load modes decided | High for read-back; risky for effects | Medium |
| Architecture leverage | Existing workout/exercise ownership | Existing stats, but legacy debt | Existing feedback | Many flows |
| Migration risk | Additive, empty table | Possibly large/backfill taxonomy | None for display | Possible preference expansion |
| UI/mobile complexity | One current-exercise panel | Charts/history/edge cases | History UI | Multi-flow forms |
| AI dependency | None | None | None for minimum | Partial |
| QA complexity | Bounded ownership/reload/history | High semantic matrix | Moderate | Broad cross-flow |
| New domain truth | One explicit note | Several load semantics | None/minor | Precedence/persistence choices |
| Future optionality | History, reflection, later progression | High but premature | Coach context later | Better planning |

Candidate A is selected. Candidate B may offer more aspirational “progression feel”, but it fails the current domain-honesty gate without product decisions Atlas cannot infer. C has a mandatory copy correction but read-back alone closes a weaker next-action loop. D is valuable architecture debt with less immediate visible consequence.

## 15. Selected release thesis

**Atlas v0.11 allows a user to save a note for an exercise during a workout, persists that explicit session memory, and returns it with the last completed sets when the exercise appears again, without inferring progression, readiness, pain meaning or the next load.**

The release remains coherent with every SHOULD removed.

## 16. User journey

| Step | Contract |
|---|---|
| ENTRY POINT | Guided session, current exercise |
| USER INTENT | Remember execution-specific context and what happened last time |
| ACTION | Review “Última vez”; enter/edit/delete current exercise note; explicitly save |
| CONFIRMATION | Saved state with date/version; conflict reload if stale |
| PERSISTED TRUTH | Note owned by user/workout/exercise; sets remain existing rows |
| READ-BACK | Current note after reload; latest completed note and latest completed set encounter, each labeled by date |
| HISTORICAL EFFECT | Once workout closes, its note becomes immutable historical input for a later encounter |
| FEEDBACK EFFECT | No score; raw note/sets only |
| NEXT USEFUL ACTION | User chooses reps/weight using their judgment |
| EMPTY STATE | “Todavía no hay una sesión anterior registrada para este ejercicio.” |
| ERROR STATE | Context unavailable is not replaced with zero/demo data; note draft stays local |
| RETURN VISIT | Reload resumes saved current note; later workout receives prior completed context |
| MOBILE | Collapsible panel above inputs; no modal required; 44px controls, dates/sets wrap |

Atlas adds value by retrieving owned history at the moment it is useful. It merely displays raw sets; it does not decide the next load.

## 17. Product contract

### Entities and ownership

`WorkoutExerciseNote`

- `id` integer PK autoincrement;
- `userId` FK users;
- `workoutId` FK workouts;
- `exerciseId` FK exercises;
- `note` trimmed text, 1–280 Unicode code points;
- `version` integer >=1;
- `createdAt`, `updatedAt`.

Unique `(workout_id, exercise_id)`. Ownership is defense in depth: `userId` must match workout owner; service never accepts it from the request body.

`ExerciseSessionContext` is a read model, not a table:

- current saved note for requested active workout/exercise;
- `lastCompletedSets`: latest completed, non-deleted owned workout containing eligible sets for exact exercise;
- `lastCompletedNote`: latest completed, non-deleted owned workout containing a note for exact exercise;
- the two historical sources may be different workouts and carry independent Córdoba dates/workout IDs.

### Eligibility

An exercise may receive a current note if it is accessible to the user and either:

1. belongs to the workout's routine, including a skipped/held item; or
2. already has a non-deleted set in that workout (manual workout path).

Historical sets are eligible only when:

- workout belongs to user, `deletedAt IS NULL`, `endedAt IS NOT NULL`;
- set has exact `exerciseId`, `completed=true`, `deletedAt IS NULL`;
- reps and weight already satisfy persisted schema/service invariants.

No current/open workout contributes to “last completed”.

### Lifecycle

- Create/update/delete only while workout is active.
- PUT uses CAS `{noteId, version}`: both null to create; exact pair to update.
- Identical PUT is idempotent and returns existing row without version bump.
- DELETE requires exact pair; repeated delete with no replacement is idempotent.
- Closing workout freezes note; no note mutation after `endedAt`.
- A saved note remains if exercise is skipped/held. It describes that workout encounter; UI must not imply a completed set.
- Soft-deleting workout excludes its notes and sets from future context.
- Soft-deleting custom exercise makes it inaccessible under existing ownership rules; no separate history recovery UI in v0.11.
- Note text is user-declared, not medical data interpreted by Atlas.

### Mutation/concurrency/idempotency

Route validates → auth → service. Transaction verifies workout state, owner, exercise eligibility and the following transition table; note writes do not modify queue, routine, sets, plan, feedback or Coach recommendation.

| Operation / observed state | Result |
|---|---|
| PUT `{null,null}` and no row | create version 1; `201` |
| PUT `{null,null}` and row has the same normalized note | idempotent create retry; `200`, no version bump |
| PUT `{null,null}` and row has different normalized note | `409 CONFLICT` |
| PUT exact current `{id,version}` and different normalized note | update atomically, version +1; `200` |
| PUT same id with any stale-or-current version and same normalized note | idempotent update retry; `200`, return current row, no version bump |
| PUT otherwise (different id, stale version with different note, disappeared/replaced row) | `409 CONFLICT` |
| DELETE exact current `{id,version}` | delete; `200 {note:null}` |
| DELETE and no row exists | idempotent retry; `200 {note:null}` |
| DELETE when a different/recreated current row exists | `409 CONFLICT` |

The service resolves each case inside one transaction. A conditional write that loses a race must re-read the row in that transaction and apply the table; “zero affected rows” alone is not automatically a conflict. Tests must force create/create, update/update and delete/recreate races, not only sequential retries.

### Time/date semantics

Ordering uses `workouts.endedAt DESC, workouts.id DESC`. Display date is `cordobaLocalDate(endedAt)`. `startedAt` may be shown as secondary timestamp but never decides which completed encounter is latest.

### Retention/privacy

Notes persist with workout history. No export/retention policy changes. Notes are never sent to Gemini, Telegram, analytics or another user. A future privacy/export/delete feature must include this table; v0.11 does not create a new retention category beyond user-authored workout history.

### Historical compatibility/backfill

Migration creates an empty table. No synthetic notes. Existing sets/workouts need no backfill. Previous sessions with no note still provide set context. Current local-only drafts cannot be recovered and are not migrated.

## 18. Metric and data semantics

v0.11 introduces no score, ratio, trend or recommendation.

| NAME | SOURCE | NUMERATOR / DENOMINATOR | WINDOW | MINIMUM DATA | FORMULA / ROUNDING | PROVENANCE | MEANING | DOES NOT MEAN | EMPTY / ERROR |
|---|---|---|---|---|---|---|---|---|---|
| `lastCompletedSets` | workouts + workout_sets | n/a | latest eligible encounter, all-time lookback bounded query | one eligible set | raw ordered by `setIndex,id`; no rounding | `user_input` values, selected by `atlas_computed` rule | exact reps/weight entered last completed encounter | recommended load, working sets, PR, progression | empty if none; error never becomes empty |
| `lastCompletedNote` | workout_exercise_notes + workouts | n/a | latest eligible completed note, all-time bounded query | one frozen note | trim only; no summarization | `user_input` | user's last saved text for exercise | diagnosis, Coach insight, instruction | empty if none; error explicit |
| `currentNote` | workout_exercise_notes | n/a | current workout | saved note | exact persisted text/version | `user_input` | saved draft for current encounter | historical fact until workout closes | local draft retained on error |

Decimal values remain strings. The UI may format a weight with unit but does not calculate delta or percent. Set order is historical `setIndex`; gaps are allowed.

## 21. Architecture

### Database

Add `workout_exercise_notes` after `0023`:

```text
id INTEGER PRIMARY KEY AUTOINCREMENT
user_id INTEGER NOT NULL REFERENCES users(id)
workout_id INTEGER NOT NULL REFERENCES workouts(id)
exercise_id INTEGER NOT NULL REFERENCES exercises(id)
note TEXT NOT NULL
version INTEGER NOT NULL DEFAULT 1 CHECK(version >= 1)
created_at INTEGER NOT NULL
updated_at INTEGER NOT NULL
UNIQUE(workout_id, exercise_id)
INDEX(user_id, exercise_id, updated_at)
INDEX workouts(user_id, ended_at DESC, id DESC) WHERE deleted_at IS NULL AND ended_at IS NOT NULL
INDEX workout_sets(exercise_id, workout_id, set_index, id) WHERE deleted_at IS NULL AND completed = 1
```

The two final indexes are additive changes on existing tables; they do not change set/workout fields or semantics. SQLite `length(trim(note))` may be a defensive check, but the shared TypeScript helper is canonical and must count Unicode code points with `Array.from(normalized).length`, not UTF-16 code units. No backfill. Rollback drops the new table and these two indexes; it loses only v0.11 notes, so export before production rollback. Deploy migrate → app → smoke.

### Domain

- `types/exercise-session-memory.ts` owns DTOs/unions.
- Pure validation/normalization for note and total parser guards.
- Canonical eligibility query/service, not JSX/route logic.
- Exact `exerciseId`; no name/slug merging.
- Dates from `endedAt` in Córdoba.

### Services

- `getExerciseSessionContext(userId, workoutId, exerciseId)`;
- `putWorkoutExerciseNote(userId, workoutId, exerciseId, input)`;
- `deleteWorkoutExerciseNote(...)`;
- internal bounded `loadLastCompletedExerciseSets` and `loadLastCompletedExerciseNote`.

Queries use the additive indexes above: select the latest eligible workout by `(user_id, ended_at DESC, id DESC)`, verify an eligible exact-exercise set through the partial set index, then load only that workout's sets; last note uses its note index and `LIMIT 1`. Packet B must capture `EXPLAIN QUERY PLAN` evidence that both latest-history paths use indexes and do not sort/scan the full history. The response and second-stage set load are bounded; if SQLite cannot prove this plan, implementation stops for Architecture review rather than retaining the scalability claim.

### API

| Method | Endpoint | Request | Response | Errors |
|---|---|---|---|---|
| GET | `/api/workouts/[id]/exercises/[exerciseId]/context` | — | typed context | 400/401/403/404 |
| PUT | same path `/note` | `{note, expectedNoteId, expectedVersion}` | 200/201 note | 400/401/403/404/409 |
| DELETE | same path `/note` | `{expectedNoteId, expectedVersion}` | 200 `{note:null}` | 400/401/403/404/409 |

Foreign workout remains `FORBIDDEN` to match workout routes; inaccessible exercise follows ADR-005 `NOT_FOUND`. Finished workout mutation is `VALIDATION`. Error body remains `{code,message}`.

### Client/hooks

- `lib/api/exercise-session-memory.ts`: total response parser and typed error.
- `hooks/useExerciseSessionMemory.ts`: key by workout/exercise; abort stale exercise request; preserve current data during save; refetch after write/conflict.
- Save is explicit, not debounce/autosave; draft stays local on network failure.

### UI

- Existing Notes panel becomes persisted and shows save/delete/status.
- New “Última vez” panel on current exercise shows independently dated last sets and last note.
- Empty/loading/error states are local to panel and never block set logging.
- Prior weights/reps are read-only.
- No new top-level navigation in MUST.
- Feedback helper copy corrected.
