## 2. Owner decisions and selected design

Use one persistent, dedicated production smoke user; API-created synthetic fixture; API-level note deletion and workout soft deletion; manual `workflow_dispatch` from trusted code; a `production-qa` GitHub Environment; one concurrent run; sanitized machine-readable evidence. **No direct production DB credential in the smoke workflow. No arbitrary SQL, QA-only endpoint, admin role, auth bypass, session minting endpoint, or production runtime change is proposed.** The account has no human owner and must never link Telegram. It has only ordinary user permissions. Its email is a controlled operational identifier, not `qa@atlas.test`; choose and record it at one-time provisioning without embedding a password in source.

Why selected: an ordinary user credential can access only its own app data through existing ownership checks. The previous design exposed a production database token to CI and required physical deletion of user/children. Here, retention of soft-deleted rows follows Atlas product semantics. The primary long-lived secret is the QA password; account misuse is contained to this user's data but can still pollute its metrics or consume shared rate limits. A leaked password is not harmless.

The existing auth session cookie is `HttpOnly`, `Secure` in production, `SameSite=Lax`, signed, and backed by a revocable session row. Maximum lifetime is seven days. Logout revokes only the current session. No password-change/reset API is present. Credential rotation or emergency revocation therefore needs an out-of-band owner-controlled account maintenance procedure; it must never be implemented as SQL in the smoke workflow. The account must be provisioned and validated before the first smoke; if absent or login fails, the workflow stops without creating another user.

## 3. Verified API primitives

| Need | Existing route and observed behavior |
|---|---|
| Login/logout/identity | `POST /api/auth/login` issues real session cookie; `POST /api/auth/logout` revokes current session; `GET /api/auth/me` confirms identity. Login has durable 10/min/IP limit by default. |
| Exact exercise | `GET /api/routines` lists system/owned routines with ordered exercises. Choose a system routine containing a valid exact exercise; no custom routine needed. |
| Create/list/find | `POST /api/workouts` accepts `{routineId}` and returns 201/ID; `GET /api/workouts` lists only owned, nondeleted workouts; `GET /api/workouts/active` returns an owned active workout or `null`; `GET /api/workouts/:id` returns owned workout plus sets. One active workout per user is enforced by a partial unique index. |
| Mark/close/delete | `PATCH /api/workouts/:id` accepts `note` and `endedAt`; use `note` as run marker. Closing updates streak. `DELETE /api/workouts/:id` soft-deletes with owner check; list and active reads exclude it. Repeated DELETE returns 404, which recovery may accept only after confirming absence from list. |
| Sets | `POST /api/workouts/:id/sets` accepts exact `exerciseId`, positive `setIndex/reps`, decimal-string `weightKg`; creates completed set. Set updates exist, but are unnecessary. |
| Context/note | `GET /api/workouts/:id/exercises/:exerciseId/context` returns current note and latest completed exact-exercise sets from nondeleted workouts, excluding current workout. `PUT .../note` creates with `{note,expectedNoteId:null,expectedVersion:null}` and returns row ID/version/owner. `DELETE .../note` requires exact `{expectedNoteId,expectedVersion}`, works only while workout is active, and returns `{note:null}`. |

No API primitive is missing for workout fixture creation, discovery, note removal, or product-visible fixture cleanup. A derived streak reset is unnecessary under the explicit owner acceptance in §8.

## 4. Exact recurring HTTP lifecycle

Precondition: trusted workflow has verified its ref, deployment target, secret availability, and single-run lock. It never registers a user.

1. Generate random nonsecret `qaRunId`. `POST /api/auth/login` with configured dedicated email/password, store cookie only in a private in-memory jar. `GET /api/auth/me` must match exact expected email and return user ID. A no-cookie protected request should return 401.
2. Before creating anything, `GET /api/workouts/active` and `GET /api/workouts`. Recover prior clearly marked QA artifacts under §6. Any unknown active/visible workout halts the smoke, except an unmarked active workout that can be proven to be the only just-created orphan within the expected time window; quarantine ambiguity rather than deleting it.
3. `GET /api/routines`; choose a system routine and exact member exercise. Fail if none. `POST /api/workouts {routineId}` → historical workout A. Immediately `PATCH /api/workouts/A {note:"ATLAS_SMOKE:<qaRunId>:history"}` and record A in a restricted, secret-free manifest. The short create-before-mark crash window is recovered through `GET active` because only one active workout can exist for this dedicated user; verify owner, routine, creation time, and absence of human use before soft delete.
4. `POST /api/workouts/A/sets` twice with `{exerciseId,setIndex:1|2,reps:8|10,weightKg:"42.5"|"40"}`. `PATCH /api/workouts/A {endedAt:<current ISO time>}`. This triggers streak materialization (§8).
5. `POST /api/workouts {routineId}` → current workout B. Immediately `PATCH /api/workouts/B {note:"ATLAS_SMOKE:<qaRunId>:current"}` and record B. `POST /api/workouts/B/sets` once for E with `setIndex:1,reps:3,weightKg:"99"`. `GET /api/workouts/B/exercises/E/context`: `currentNote:null`; `lastCompletedSets` must reference A, contain its raw decimal strings/IDs, and exclude B's deliberately different open-workout set. No progression, PR, e1RM, recovery, recommended load, or readiness assertion.
6. `PUT /api/workouts/B/exercises/E/note` with a short synthetic marker and null CAS pair → 201. Assert returned `id` positive, `version:1`, exact note, `userId` equals `/auth/me`, `workoutId:B`, `exerciseId:E`. `GET context` must reflect it. A stale CAS PUT should return 409 without changing text.
7. `POST /api/auth/logout`; replay the captured first signed cookie against protected context and require 401, proving revocation. Then discard it. `POST /api/auth/login` again; require a fresh session cookie, `/auth/me` identity match, and context with persisted note ID/version/text and the same raw history. This proves login/session and application persistence separately.
8. Before closing/deleting B, `DELETE .../note` with the exact current ID/version; assert `currentNote:null`. `DELETE /api/workouts/B`, then `DELETE /api/workouts/A`. `GET /api/workouts` must omit both IDs; `GET /api/workouts/active` must be `null`; `GET /api/workouts/{A|B}` and B context must return 404. Nonproduction tests prove that a later new QA workout's context for E does not return A as previous history.
9. `GET /api/stats/streak` after cleanup to force recomputation of current streak/last active date from visible records; with this exclusive QA account and no other activity, require `currentStreak:0` and `lastActiveDate:null`, while recording the accepted `longestStreak` residual as non-evidence. `POST /api/auth/logout` and replay the captured second cookie against a protected API; require 401. Mark run `PASS` only if target, auth, context, persistence, and product-visible fixture cleanup succeed.

The note must be deleted **before** workout B is closed or soft-deleted. If it was already closed by a prior failed run, note DELETE cannot succeed; soft-delete hides it from product reads, and the physical row remains under ordinary Atlas semantics. No real user data is read or written.

The password owner is Release/Infra, readers are only the reviewed job and authorized environment maintainers, scope is the ordinary QA user, lifetime is until rotation, and failure on missing/invalid value is immediate. ## 6. Orphan recovery, concurrency, and cleanup

Each run uses `ATLAS_SMOKE:<qaRunId>:<role>` in the workout `note` field and a secret-free manifest with expected QA user ID, routine/exercise, A/B IDs, timestamp, and workflow run ID. The password and cookies never enter the manifest. Preflight and `always()` cleanup use only the QA session and owned APIs. `GET /api/workouts` returns all visible workouts for the QA user, including completed ones; `GET active` finds a stale active workout. For each marked artifact, `GET /api/workouts/:id` confirms owner and marker before mutation. For active B, context retrieves current note CAS pair and deletes it, then soft-deletes B. For A, soft-delete even if complete. A soft-deleted artifact disappears from list and active; a retry treats 404 as already cleaned only after readback confirms absence. Unknown markers, multiple ambiguous unmarked workouts, unexpected user ID, wrong routine, or a record outside the window stop cleanup and alert the owner; never delete merely by guessed ID.

A cancellation may bypass `always()` and leave that session active for up to seven days; the runner cannot revoke a lost session cookie through existing APIs. Next manual dispatch begins with preflight reconciliation; add a protected recovery-only dispatch that performs the same API-only cleanup and never creates a fixture. Operational monitoring must flag stale manifests/active QA workouts so a release owner runs recovery; no silent indefinite orphan. Emergency invalidation of all account sessions belongs to the owner maintenance procedure, not the smoke workflow. One active workout index plus workflow concurrency serialize normal runs. A leaked password or out-of-band login can race despite workflow serialization; wrong session/account or unexpected workout is a stop condition. Soft-deleted data remains physically stored under product semantics. Note deletion is hard delete if B remains active; otherwise the note persists physically under its soft-deleted workout but is no longer reachable through normal context.

**Cleanup contract: PRODUCT-VISIBLE FIXTURE CLEANUP, not full physical or derived-state restoration.** Success means the smoke note is deleted when its workout remains active, synthetic workouts are soft-deleted through authenticated APIs, they no longer participate in exercise-session history or ordinary workout/Progress views, no smoke workout remains active, the current session is logged out/revoked, a fresh login was proven, and no unrelated user's data was touched. Verify: `GET /api/workouts` omits run IDs, `GET active` is null, direct workout/context reads are 404, and nondeleted-workout filters remove A from prior-set context and stats/progress calculations. A failed cleanup yields `FAIL`, never a partial pass. Physical rows and the accepted QA-only `longestStreak` may remain (§8).
