## 2. Thesis options considered

| Thesis | Benefit | Reason to accept or reject |
|---|---|---|
| A. Ship charts and PR badges from `weight_kg` | Fast visible result | Reject: the same number may mean external load, added load, assistance or an ambiguous per-hand entry; current PR includes unfinished work. |
| B. Establish typed set facts, explicit eligibility and exact comparison before claims | Enables defensible PR and later views | **Select**: additive, testable and compatible with legacy history as raw observations. |

## 3. Selected thesis and why now

**Progression Foundation = preserve what was recorded, capture what each new set means, and permit a claim only when the input and comparison key support it.** The workout engine and last-session memory now provide stable write/read boundaries. A visual progression layer built before semantic capture would turn an ambiguous `weight_kg` into false precision. This wave builds the domain contract and a narrow read model first. It does not create an exercise recommendation or readiness system.

## 4. Scope: MUST / SHOULD / DEFER / EXCLUDE

| **SHOULD** | A single per-exercise card with the representative set from the last comparable closed workout and the best eligible set; versioned provenance/reason codes; migration coverage and count of records excluded by unknown semantics; clear copy for raw legacy sets. |
| **DEFER** | Bodyweight/assisted PRs, e1RM, rep-range or volume PRs, body-mass-normalized estimates, cross-exercise equivalence, muscle map, ranking, quests/streak changes, animation, design system overhaul. These need explicit separate contracts/research. |

## 5. Explicit domain glossary

| Term | Meaning |
|---|---|
| Observation | A persisted set with its original reps and recorded decimal-string weight; may be semantically unknown. |
| Load mode | How external resistance relates to the movement: `external`, `bodyweight`, `bodyweight_added`, or `assisted`. This is a recorded fact, not derived from exercise name. |
| Load basis | Whether the recorded external value is `total_external` or `per_side_external`; never silently multiply or convert. |
| Side | `bilateral`, `left`, `right`, or `alternating`; alternating requires an explicit rep-count basis before any comparable claim. |
| Set purpose | User-declared `working` or `warmup`; `unknown` for old records and omitted new values during transition. |
| Eligible set | A completed, live set in an owned, closed, live workout with all semantics needed by the named metric. |
| Comparable | Two eligible observations with identical exercise identity and metric-specific semantic key. |
| Best set | The maximum within a declared metric and comparison cohort, with its selection rule shown. No universal best exists. |
| PR | A strictly improved, previously established maximum in one comparable cohort. The first eligible closed workout representative is a baseline, not a PR. |
| Unknown | Missing semantic evidence. It remains visible as raw history, never silently defaults to `working` or `external`. |

## 6. Progression truth model

Keep persisted observation facts separate from computed claims. A candidate set carries `setId`, `workoutId`, `exerciseId`, `reps`, original `weightKg` decimal string, the set's `completed` boolean and `deletedAt`, the workout's `endedAt`/`deletedAt`, declared purpose, load mode, load basis and side, plus contract version/provenance. There is **no set completion timestamp**. These facts may change while the workout is open; after close, deletion remains possible. The application computes `{ status: eligible | ineligible | unknown, reasons[] }` for a **named metric**. A read model returns the candidate workout representative, previous comparable workout representative, comparison result, and rule version. No persisted `is_pr` flag: edits, deletes and future contract changes can invalidate a derived PR. Order completed workouts by `(endedAt, workoutId)`; within a workout, `setIndex, setId` is only a stable display/tie order, not a set completion timestamp. Use the Córdoba local date only for display.

Ownership and lifecycle are checked at the query boundary. A set from an active workout is a live input to the logger but never a historical result or PR. Soft-deleted workouts, sets and inaccessible exercises are excluded. A closed workout with `completed=false` sets does not supply an eligible candidate. Invalid or missing semantic fields yield `unknown`, not zero or false.

## 7. Set taxonomy proposal

Model **purpose** first: `warmup | working | unknown`. A warm-up is excluded from all progression claims; a working set can become eligible if other fields are complete. `unknown` is the migration/default state and is excluded from claimed PRs. Do not infer purpose from set order, load, reps, routine targets or the highest weight.

`top set`, `backoff`, `drop set` and `AMRAP` describe different axes: position/role, sequence and effort protocol. They are not mutually exclusive set types. If a later wave needs them, add independently declared tags or protocol fields with definitions and validation; do not force them into one enum. A top set may eventually be *computed* as the selected eligible maximum in a workout, but that computation is not proof the user intended a top set. Drop/backoff need explicit sequence/reference semantics; AMRAP needs an explicit user declaration, not a rep threshold. Assisted/bodyweight are **load modes**, not purposes. Until those extra axes exist, show no drop/top/backoff/AMRAP labels as factual user input and grant them no distinct PR category.

## 8. Load semantics proposal

Persist the original `weight_kg` without changing historical values. For new sets, record a mode and a decimal-string external amount with an explicit basis. `external` means positive external resistance only; `bodyweight` means no external amount (`weight_kg='0'`, no assertion about body mass); `bodyweight_added` means positive extra external load only, not body mass + plates; `assisted` means positive magnitude of aid, with larger assistance *not* interpreted as greater strength. Zero is valid **only** for plain bodyweight mode; modes with positive amounts require a declared basis. Never calculate total system load from `weight_kg` without an explicit contemporaneous body-mass observation and a separately approved formula. Machine counterweights, elastic bands, cable ratios and weighted vests remain unknown unless the user explicitly records the applicable convention.

The current `weight_kg` column is **insufficient** to tell these apart. **Selected storage path:** retain it as the single amount field, interpreted as external amount/assistance magnitude **only when** non-null semantic contract version and mode are present; legacy null rows remain raw/uninterpreted. Add nullable semantic fields, not a second amount column. The existing `isValidWeightKg` rejects zero, so implementation must add a mode-aware validator and adjust zero formatting/entry without loosening legacy behavior accidentally. Decimal comparisons must use decimal-string utilities, never float domain assertions.

## 9. Unilateral semantics proposal

Store side at **set** level, because users may log a separate left and right set. `bilateral`, `left`, and `right` are distinct comparison cohorts. `per_side_external` is a load basis, not a side; a bilateral dumbbell movement logged as “20 kg per hand” is not comparable to “40 kg total” until a deliberate conversion rule exists. `alternating` is recorded as such but **excluded from MVP comparison and PR**, even if a user supplies `reps_per_side` or `reps_total`; a later contract must include that rep-count basis in the comparison key and define execution semantics. Do not derive laterality from the exercise catalog or halve/double reps. A future linked left/right pair can compare per side separately; an aggregate or “weaker side” metric needs its own opt-in contract.

## 10. Eligible-set and exact comparison rules

**Base eligibility:** same authenticated owner, live exercise, closed and nondeleted workout, completed and nondeleted set, positive integer reps, valid mode-appropriate decimal amount. **Metric eligibility:** `purpose=working`, supported load mode, explicit basis and supported side. The MVP PR supports `bilateral|left|right`, excluding `alternating`. Warm-up and unknown are excluded from PR and best-set claims. The raw previous-session memory remains available, labeled “series registradas” and never silently upgraded to comparable performance.

For the first PR metric, the comparison key is `(userId, exact exerciseId, contractVersion, loadMode=external, loadBasis, side, reps)`. Both candidates must meet the same key and base/metric eligibility. Compare decimal external amount strictly (`>`); equality is a tie, not a new PR. An older `exerciseId` is not equivalent to a renamed/related exercise unless a separately approved, explicit identity mapping exists. Technique, ROM, equipment, tempo and machine calibration are **not captured**; the copy must say “mayor carga externa registrada para estas mismas repeticiones y condiciones registradas”, never “stronger” or “true one-rep max”. Since these uncaptured variables matter, offer a way to view the source set and avoid global rank claims.

## 11. Minimum viable PR eligibility model

**MVP PR = max positive external load for the same exact exercise, same reps, same declared basis and supported side, among completed working sets in closed workouts.** A prior eligible **workout** in the cohort is required. For each closed workout and cohort, select its highest eligible set; ties in that workout choose lowest `(setIndex, setId)` as source. Compare that workout representative against the maximum from **earlier closed workouts**, ordered by `(endedAt, workoutId)`: first result `baseline`, later strictly greater result `new_pr`, equal result `ties_best`, lower result `below_best`. The display may show the best set, but the PR classification belongs to the completed workout and selected source set, not to an inferred intra-workout moment; `workout_sets` has no per-set completion timestamp. Determine current best from all eligible closed workouts in the cohort; use recency only to display a tie, never to call it a new PR. Recomputing against current data may retract a prior result after deletion; surface current truth, not an immutable trophy.

Bodyweight may later support **rep-only** records within a declared mode/side cohort, but body mass and execution standards are absent, so no added-load/equivalent-load claim now. Assisted sets need a separate “less assistance at same reps” metric and equipment convention; neither qualifies for the MVP PR. `bodyweight_added` could support an **added external load** PR later, explicitly separate from `external` and without total-body-mass claims. e1RM requires a named formula, input range, applicability, version and uncertainty presentation; it is out of v0.12.

## 12. Historical comparison model

Expose two parallel read paths: (1) raw last completed exact-exercise session, continuing the v0.11 memory contract; (2) last **comparable eligible** workout representative and best eligible set in one explicit cohort. A workout may have multiple sets; pick its representative by the named metric and return source IDs, workout-close timestamp, reps, decimal amount, status and reason codes. “Previous” means the last *eligible comparable* closed workout strictly before the candidate workout by `(endedAt, workoutId)`, not simply the last workout; if the last workout contains only warm-ups/unknown modes, explain why it is skipped. Never join by exercise name, muscle group, routine, media URL or notes. Use bounded/keyset pagination for history; avoid loading all sets as current `getExerciseHistory` does. Historic legacy sets remain inspectable but return `unknown_semantics` for progression.

## 13. Data and schema implications

The current workout/workout_set schema is sufficient for raw history and exact-exercise prior sets, **not** truthful multi-mode progression. Proposed additive change: nullable semantic version, purpose, load mode, load basis, side, and alternating rep basis; keep `weight_kg` as the single amount field under the versioned interpretation above. Add CHECK constraints for enum values, amount/mode combinations and side/rep-basis combinations, with a staged migration/read rollout. All existing rows migrate to null/unknown semantics; no backfill from exercise catalog, positive weight, notes or UI defaults. New writes should require declared supported semantics after a transitional client rollout; old clients may continue only into a documented raw/unknown path, never automatically eligible. Check indexes for `(exercise_id, workout_id)` and ordered owned completed workouts, then add a selective history index only if query plans justify it. Avoid a stored PR table in v0.12; if performance later demands one, define invalidation for edits/deletes and version changes first.

`workout_exercise_notes` is separate free text. It can be displayed beside source sets as user context but must never be parsed for load type, pain, recovery or eligibility. `post_workout_feedback` is workout-level input and likewise cannot qualify a set or infer readiness. Reconcile existing `stats.ts`, `/api/stats/prs`, legacy badge, `isPR`, and progress labels so no old surface keeps asserting an unsafe PR after a new service exists. ADR-001's historical max-weight wording needs a scoped addendum/decision before replacing its public contract.

## 14. API, DTO and service implications

Domain-first sequence: typed pure `classifySet`, `comparisonKey`, `comparePerformance`, `selectPrevious`, `selectBest` with reason codes and exhaustive tests; then persistence/validation; then bounded read service; then thin routes/UI. Suggested shared DTO: `ProgressionObservation` (raw persisted facts + provenance), `EligibilityResult`, `ComparableSet` (only after classification), `ComparisonResult` (`baseline|improved|equal|lower|incomparable|unknown` with reason), `PersonalRecordResult` (`new_pr|ties_best|below_best|baseline|unknown`), and `ExerciseProgressionSummary`. Include `contractVersion` and source IDs to make each claim auditable. Existing `Metric<T>` should wrap displayed computed values with `atlas_computed`, while logged values remain `user_input`.

Future authenticated surfaces: versioned `GET /api/exercises/:id/progression?limit&cursor` and/or `GET /api/stats/exercises/:id/progression`, scoped by owner and exact ID; `POST/PATCH` set routes gain semantic fields and validation. Response must distinguish `no_history`, `history_without_semantics`, `no_comparable_set`, and `ready`. Do not broaden `GET /api/stats/prs` silently: either version its response or introduce a new endpoint and migrate consumers intentionally. Route handlers only validate/authenticate/call service/map `{code,message}` errors. Test negative ownership, live/deleted/incomplete rows, decimal ordering, ties, same-workout representative selection (not temporal PR sequence), and legacy unknowns.

## 15. UX surfaces enabled by the foundation

Safe first outputs: exact raw prior session (“última sesión registrada”), representative set from the last comparable closed workout, and best eligible set **with metric name and source**; a narrowly labeled same-reps external-load PR only after the semantic writer/read path and old PR consumers are reconciled. Show empty/unknown/loading/error separately. A per-exercise card can link to source workout and explain “sin comparación válida” when fields differ. Historical values may be shown verbatim without trend/PR language. Future strength charts can plot one compatible cohort at a time; do not connect mixed exercises, reps, sides or modes with a line. Future milestones/celebrations consume only validated `new_pr` events. A future body map needs a vetted exercise-to-muscle mapping plus an explicitly defined aggregate; the current `muscleGroup` string is not a physiological score.

## 16. Future design, motion and engagement direction — separate wave

The product can become more distinctive through a coherent icon set, original movement illustrations, clearer hierarchy, useful feedback after a verified record, and purposeful motion. First conduct an icon/illustration audit: current generic/uneven symbols should be evaluated for semantic clarity at mobile size, contrast and accessibility; choose a custom visual language only after comparing production screens, then prototype rather than replacing all icons at once. Motion should mark state changes (set saved, comparison available, validated PR) with restrained timing and reduced-motion equivalents. A celebration must be triggered by a verifiable event, not by a first baseline or ambiguous legacy record.

`framer-motion`/current **Motion for React** is a plausible later fit for React microinteractions; [official docs](https://motion.dev/docs/react) confirm the maintained React API. Evaluate bundle/performance, SSR behavior and `prefers-reduced-motion` in a small prototype before adoption. **Three.js** belongs only in a later body-map discovery if 2D SVG cannot meet an agreed interaction need; its [WebGL renderer](https://threejs.org/docs/pages/WebGLRenderer.html) introduces graphics capability/performance considerations. `img2threejs` is not validated as an Atlas dependency or product requirement; research its actual tool/licensing/output quality separately before proposing it. Neither library belongs in v0.12 foundation.

Sequence: truthful set capture → comparable per-exercise read model → accessible, clear 2D progress visualization → event-based celebratory feedback → body-map research and optional 3D prototype → engagement experiment. Separate future discoveries: visual identity/iconography, motion/microinteraction language, body-map anatomy and metric semantics, and motivation/quest mechanics. Each needs its own user problem, success measure and accessibility guardrail.

## 22. Independent review findings and resolution

First independent verdict: **BLOCK**. The reviewer found three contract gaps: alternating sets could have compared identical rep numbers with different rep-count bases; the draft treated `setIndex` as though it timestamped a set's performance inside a workout; and mode-specific zero-load validation was left undecided. The reviewer also flagged “immutable observations” as inaccurate because open-workout sets remain editable.

Document-only resolution: alternating is excluded from the MVP comparison/PR and a future rep-basis key is required (§§9–11); PR classification now belongs to a closed workout representative compared with earlier closed workouts, using `setIndex` only for deterministic source tie selection (§§6, 11–12); zero is allowed only for plain bodyweight and the mode-aware validator requirement is explicit (§8); persisted observations are described as mutable while open (§6). A second pass caught residual wording that still described a set-level baseline or an intra-workout moment; §§5–6, 14–15 and 21 were aligned with the closed-workout model. **Final independent re-review verdict: APPROVE.** The reviewer also requested the nonblocking §4 terminology alignment, now applied. This is approval of the discovery artifact's internal consistency, not PO/Architecture implementation approval.
