## 3. Selected thesis and why now

**Progression Foundation = preserve what was recorded, capture what each new set means, and permit a claim only when the input and comparison key support it.** The workout engine and last-session memory now provide stable write/read boundaries. A visual progression layer built before semantic capture would turn an ambiguous `weight_kg` into false precision. This wave builds the domain contract and a narrow read model first. It does not create an exercise recommendation or readiness system.

## 5. Explicit domain glossary

| Term | Meaning |
|---|---|
| Observation | A persisted set with its original reps and recorded decimal-string weight; may be semantically unknown. |
| Load mode | How external resistance relates to the movement: `external`, `bodyweight`, `bodyweight_added`, or `assisted`. This is a recorded fact, not derived from exercise name. |
| Amount basis | `total` or `per_side` describes the amount's counting convention, independent of load mode; `null` is required for plain bodyweight. Never silently multiply or convert. |
| Side | `bilateral`, `left`, `right`, or `alternating`; alternating requires an explicit rep-count basis before any comparable claim. |
| Set purpose | User-declared `working` or `warmup`; SQL `NULL` means unknown on legacy rows. New v0.12 writes may not omit it. |
| Eligible set | A completed, live set in an owned, closed, live workout with all semantics needed by the named metric. |
| Comparable | Two eligible observations with identical exercise identity and metric-specific semantic key. |
| Best set | The maximum within a declared metric and comparison cohort, with its selection rule shown. No universal best exists. |
| PR | A strictly improved, previously established maximum in one comparable cohort. The first eligible closed workout representative is a baseline, not a PR. |
| Unknown | Missing semantic evidence. It remains visible as raw history, never silently defaults to `working` or `external`. |

## 6. Progression truth model

Keep persisted observation facts separate from computed claims. A candidate set carries `setId`, `workoutId`, `exerciseId`, `reps`, original `weightKg` decimal string, the set's `completed` boolean and `deletedAt`, the workout's `endedAt`/`deletedAt`, declared purpose, load mode, amount basis and side, plus `semanticCaptureVersion` and provenance. There is **no set completion timestamp**. These facts may change while the workout is open; after close, deletion remains possible. The application computes `{ status: eligible | ineligible | unknown, reasons[] }` for a **named metric**. A read model returns the candidate workout representative, previous comparable workout representative, comparison result, and `progressionRuleVersion`. No persisted `is_pr` flag: deletes and future rule changes can invalidate a derived PR. Order completed workouts by `(endedAt, workoutId)`; within a workout, `setIndex, setId` is only a stable display/tie order, not a set completion timestamp. Use the Córdoba local date only for display.

Ownership and lifecycle are checked at the query boundary. A set from an active workout is a live input to the logger but never a historical result or PR. Soft-deleted workouts, sets and inaccessible exercises are excluded. A closed workout with `completed=false` sets does not supply an eligible candidate. Invalid or missing semantic fields yield `unknown`, not zero or false.

## 7. Set taxonomy proposal

Model **purpose** first: `warmup | working | unknown`. A warm-up is excluded from all progression claims; a working set can become eligible if other fields are complete. `unknown` is the migration/default state and is excluded from claimed PRs. Do not infer purpose from set order, load, reps, routine targets or the highest weight.

`top set`, `backoff`, `drop set` and `AMRAP` describe different axes: position/role, sequence and effort protocol. They are not mutually exclusive set types. If a later wave needs them, add independently declared tags or protocol fields with definitions and validation; do not force them into one enum. A top set may eventually be *computed* as the selected eligible maximum in a workout, but that computation is not proof the user intended a top set. Drop/backoff need explicit sequence/reference semantics; AMRAP needs an explicit user declaration, not a rep threshold. Assisted/bodyweight are **load modes**, not purposes. Until those extra axes exist, show no drop/top/backoff/AMRAP labels as factual user input and grant them no distinct PR category.

## 8. Load semantics proposal

Persist the original `weight_kg` without changing historical values. For new sets, `loadMode` supplies direction/meaning and neutral `amountBasis` supplies counting convention. `external` means positive external resistance; `bodyweight` requires `weight_kg='0'` as a **no external amount sentinel**, never zero physiological/system load; `bodyweight_added` means positive added external amount only, not body mass + plates; `assisted` means positive assistance magnitude, where larger assistance is not greater strength. Zero is valid **only** for plain bodyweight mode. Never calculate total system load from `weight_kg` without a contemporaneous body-mass observation and separately approved formula. Machine counterweights, elastic bands, cable ratios and weighted vests remain uncalibrated unless their convention is explicitly captured; even a recorded assisted amount is not a PR in v0.12.

The current `weight_kg` column is **insufficient** to tell these apart. **Selected storage path:** retain it as the single amount field, interpreted by `loadMode` **only when** a supported non-null `semanticCaptureVersion` and all required semantic fields are present; legacy null rows remain raw/uninterpreted. Add nullable semantic fields, not a second amount column. The existing `isValidWeightKg`/`formatWeightKg` reject zero, so implementation must use mode-aware validation, formatting and parsing; never loosen legacy validation accidentally. Decimal comparisons must use decimal-string utilities, never float domain assertions.

## 9. Unilateral semantics proposal

Store side at **set** level, because users may log separate left and right sets. `bilateral`, `left`, and `right` are distinct comparison cohorts. For a unilateral `left` or `right` set, `amountBasis=total` means the amount used by that one side; `per_side` is redundant and invalid. A bilateral dumbbell movement logged as “20 kg per hand” has `amountBasis=per_side` and is not comparable to “40 kg total” until a deliberate conversion rule exists. `alternating` is recorded as such but **excluded from MVP comparison and PR**, even when its required rep-count basis (`total|per_side`) is supplied; a later rule must include that basis in the comparison key. Do not derive laterality from exercise name/catalog or halve/double reps. A future linked left/right pair can compare per side separately; an aggregate or “weaker side” metric needs its own opt-in contract.

### 9a. Normative capture/PR combination matrix

`VALID` means valid to record **and** eligible for the MVP external-load PR if lifecycle checks pass. `RECORDED_BUT_NOT_COMPARABLE` means valid to record but excluded from this PR. `INVALID` means reject the new write. In every row, `purpose=warmup` changes a `VALID` working row to `RECORDED_BUT_NOT_COMPARABLE`; `purpose=NULL` is legacy only and cannot be written by a v0.12 client. `reps` must be a positive integer. All other combinations are `INVALID`.

| `loadMode` | `amountBasis` | `side` | `weightKg` | Working-set result | Warm-up result |
|---|---|---|---|---|---|
| `external` | `total` or `per_side` | `bilateral` | positive decimal | VALID | RECORDED_BUT_NOT_COMPARABLE |
| `external` | `total` | `left` or `right` | positive decimal | VALID | RECORDED_BUT_NOT_COMPARABLE |
| `external` | `total` or `per_side` | `alternating` | positive decimal | RECORDED_BUT_NOT_COMPARABLE | RECORDED_BUT_NOT_COMPARABLE |
| `bodyweight` | **NULL** | `bilateral`, `left`, `right` or `alternating` | exactly canonical `"0"` | RECORDED_BUT_NOT_COMPARABLE | RECORDED_BUT_NOT_COMPARABLE |
| `bodyweight_added` | `total` or `per_side` | `bilateral` or `alternating` | positive decimal added load | RECORDED_BUT_NOT_COMPARABLE | RECORDED_BUT_NOT_COMPARABLE |
| `bodyweight_added` | `total` | `left` or `right` | positive decimal added load | RECORDED_BUT_NOT_COMPARABLE | RECORDED_BUT_NOT_COMPARABLE |
| `assisted` | `total` or `per_side` | `bilateral` or `alternating` | positive decimal assistance magnitude | RECORDED_BUT_NOT_COMPARABLE | RECORDED_BUT_NOT_COMPARABLE |
| `assisted` | `total` | `left` or `right` | positive decimal assistance magnitude | RECORDED_BUT_NOT_COMPARABLE | RECORDED_BUT_NOT_COMPARABLE |

For `alternating`, `repCountBasis=total|per_side` is **required** at capture; for all other sides it **must be NULL**. `amountBasis=per_side` means an amount **per limb** in bilateral/alternating movements, independent of whether it is resistance, added load or assistance. There is no arithmetic normalization in v0.12. Unknown historical tuples have all semantic columns NULL and remain raw observations; a partially populated tuple is invalid/corrupt, never inferred. The pure validator and its table-driven tests must implement every row and the catch-all invalid cases.

### 9b. Version compatibility and typed reason codes

`semanticCaptureVersion=1` names the meaning of the persisted axes. `progressionRuleVersion=1` names the eligibility/comparison algorithm and appears on computed results, never as part of the persisted set. `canonicalSemantics(captureVersion, fields)` returns a canonical tuple or typed `unknown`; version 1 maps directly to the table above. Future capture version 2 may map to the **same** tuple if Architecture explicitly proves semantic equivalence, so differing capture versions do not automatically split cohorts. An incompatible version has no mapping under rule 1 and cannot compare; a new rule version can later define a new mapping without rewriting historical rows. The cohort key uses the canonical tuple, not raw version equality. Any change to compatibility requires test vectors with mixed-version pairs and a documented rule-version bump.

Initial `EligibilityResult` is a discriminated union: `{status:'ELIGIBLE', reason:'eligible'}`; `{status:'UNKNOWN', reason:'unknown_semantics'|'unsupported_capture_version'|'invalid_semantic_combination'}`; or `{status:'INELIGIBLE', reason:'warmup'|'unsupported_load_mode'|'unsupported_side'|'open_workout'|'incomplete_set'|'deleted_set'|'deleted_workout'|'exercise_unavailable'|'invalid_amount'}`. Missing mode/basis/side/purpose collapses to `unknown_semantics` because the remedy is the same: no claim; the read model may include a separate `missingFields[]` for UI help without expanding the reason vocabulary. Authorization failures are `NOT_FOUND`/`FORBIDDEN` at the API boundary, not public eligibility reasons. A valid, recorded bodyweight/assisted/added-load working set receives `unsupported_load_mode` **for the external PR metric**, never `invalid_amount`. Reason codes are transport data; Spanish UI/Telegram copy maps from them separately.

## 10. Eligible-set and exact comparison rules

**Base eligibility:** same authenticated owner, live exercise, closed and nondeleted workout, completed and nondeleted set, positive integer reps, valid mode-appropriate decimal amount and a compatible canonical semantic tuple. **Metric eligibility:** `purpose=working`, `loadMode=external`, explicit `amountBasis=total|per_side` and supported side. The MVP PR supports `bilateral|left|right`, excluding `alternating`. Warm-up and unknown are excluded from PR and best-set claims. The raw previous-session memory remains available, labeled “series registradas” and never silently upgraded to comparable performance.

For the first PR metric, the comparison key is `(userId, exact exerciseId, canonical loadMode=external, canonical amountBasis, canonical side, reps)`. Both candidates must meet the same key and base/metric eligibility under the **same progression rule version**; capture versions may differ if the compatibility function maps both to the same canonical tuple. Compare decimal external amount strictly (`>`); equality is a tie, not a new PR. An older `exerciseId` is not equivalent to a renamed/related exercise unless a separately approved, explicit identity mapping exists. Technique, ROM, equipment, tempo and machine calibration are **not captured**; the copy must say “mayor carga externa registrada para estas mismas repeticiones y condiciones registradas”, never “stronger” or “true one-rep max”. Since these uncaptured variables matter, offer a way to view the source set and avoid global rank claims.

## 11. Minimum viable PR eligibility model

**MVP PR = max positive external load for the same exact exercise, same reps, same declared basis and supported side, among completed working sets in closed workouts.** A prior eligible **workout** in the cohort is required. For each closed workout and cohort, select its highest eligible set; ties in that workout choose lowest `(setIndex, setId)` as source. Compare that workout representative against the maximum from **earlier closed workouts**, ordered by `(endedAt, workoutId)`: first result `baseline`, later strictly greater result `new_pr`, equal result `ties_best`, lower result `below_best`. The display may show the best set, but the PR classification belongs to the completed workout and selected source set, not to an inferred intra-workout moment; `workout_sets` has no per-set completion timestamp. Determine current best from all eligible closed workouts in the cohort; use recency only to display a tie, never to call it a new PR. Recomputing against current data may retract a prior result after deletion; surface current truth, not an immutable trophy.

Bodyweight may later support **rep-only** records within a declared mode/side cohort, but body mass and execution standards are absent, so no added-load/equivalent-load claim now. Assisted sets need a separate “less assistance at same reps” metric and equipment convention; neither qualifies for the MVP PR. `bodyweight_added` could support an **added external load** PR later, explicitly separate from `external` and without total-body-mass claims. e1RM requires a named formula, input range, applicability, version and uncertainty presentation; it is out of v0.12.

## 12. Historical comparison model

Expose two parallel read paths: (1) raw last completed exact-exercise session, continuing the v0.11 memory contract; (2) last **comparable eligible** workout representative and best eligible set in one explicit cohort. A workout may have multiple sets; pick its representative by the named metric and return source IDs, workout-close timestamp, reps, decimal amount, status and reason codes. “Previous” means the last *eligible comparable* closed workout strictly before the candidate workout by `(endedAt, workoutId)`, not simply the last workout; if the last workout contains only warm-ups/unknown modes, explain why it is skipped. Never join by exercise name, muscle group, routine, media URL or notes. Use bounded/keyset pagination for history; avoid loading all sets as current `getExerciseHistory` does. Historic legacy sets remain inspectable but return `unknown_semantics` for progression.

## 13. Data and schema implications

The current workout/workout_set schema is sufficient for raw history and exact-exercise prior sets, **not** truthful multi-mode progression. Add exactly these nullable `workout_sets` columns: `semantic_capture_version INTEGER`, `load_mode TEXT`, `amount_basis TEXT`, `side TEXT`, `set_purpose TEXT`, `rep_count_basis TEXT`. Keep `weight_kg TEXT NOT NULL` as the **only** amount field. Legacy rows retain all six semantic columns NULL and their original weight string unchanged. New v0.12 writes store `semantic_capture_version=1`, one valid `load_mode`, `side`, `set_purpose`; `amount_basis` is NULL only for bodyweight; `rep_count_basis` is non-NULL only for alternating. There is no persisted `progression_rule_version`: it belongs to the derived read model.

Migration is additive and has **zero semantic backfill**. SQLite CHECKs should constrain enum membership for the current axes, all-legacy-NULL versus a complete semantic tuple, positive-integer `semantic_capture_version` (without hardcoding `=1`), `bodyweight → amount_basis IS NULL AND weight_kg='0'`, non-bodyweight → basis present, and alternating ↔ rep-count basis present. The v0.12 service accepts **only version 1**; a future version 2 using the same fields can be admitted by a later service/compatibility change without rewriting history or this version-neutral CHECK. A genuinely new enum value or field would require its own additive migration and tests. For non-bodyweight positive decimal precision/range, use the pure parser/service because SQLite casts can accept malformed text; CHECKs are defense in depth, not the sole validator. **All newly created sets** require complete v1 semantics after the coordinated rollout. An existing pre-v0.12 legacy row may receive permitted nonsemantic edits while its workout is open, but must keep the entire semantic tuple NULL; no conversion/backfill path exists in this wave. An outdated client trying to create a set receives a typed validation error and refresh instruction; it must never silently create a new unknown row. A rollout gate must keep read paths tolerant before write enforcement and update web, Telegram and fixture clients together. No existing row is rewritten by the migration, no release work occurs in this discovery.

**History pagination and exact all-time PR are separate queries.** Existing `workout_sets_exercise_lookup_idx` on `(exercise_id, workout_id, set_index, id)` and `workouts_user_id_ended_at_idx` are starting points for the **bounded page**: owner-filtered exact exercise, strict limit, keyset cursor `(ended_at, workout_id, set_index, set_id)`. The page limit must never affect the PR answer. The separate exact aggregate query selects the best eligible closed-workout representative in the requested cohort over **all** history (and separately the best before the current workout); it may not take its maximum from the visible page. Its amount ordering must be decimal-exact. For v1 writes, normalize the positive decimal string (no redundant leading/trailing zeros) and index deterministic SQLite **string expressions** for `(length(integer part), integer part, fractional part)` in descending order, with exact cohort filters; lexicographic fraction comparison is correct for canonical nonnegative decimals, including a shorter fraction prefix. The query still joins `workouts` to enforce owner, close and delete state. A compatible future capture version must preserve this amount grammar or add an equivalent indexed normalization strategy before joining the same PR cohort; no float cast or second persisted amount column is planned.

`EXPLAIN QUERY PLAN` tests must verify both access patterns and deterministic prior-workout exclusion on a realistically large multi-user fixture: indexed exact-cohort top lookup for the aggregate, indexed bounded page for history, and no N+1/full-history sort on the request path. If the existing indexes cannot support them, an additive expression/partial index is required **before** PR exposure; if the plan still scans an unbounded cross-user set, the implementation gate blocks that read model rather than returning a page-dependent or approximate PR. `setIndex` is a deterministic within-workout source tie key, not a completion time. Avoid a stored PR table in v0.12; if performance later demands one, define invalidation for deletes and rule-version changes first.

`workout_exercise_notes` is separate free text. It can be displayed beside source sets as user context but must never be parsed for load type, pain, recovery or eligibility. `post_workout_feedback` is workout-level input and likewise cannot qualify a set or infer readiness. ADR-001's historical max-weight PR wording is superseded **for new user-facing progression claims** by this owner-approved v0.12 contract; implementation should append an ADR-001 decision note alongside its code change, preserving the old text as history.

## 14. API, DTO and service implications

Domain-first service split: pure `validateSemanticSet`, `canonicalSemantics`, `classifyEligibility`, `cohortKey`, `selectWorkoutRepresentative`, `compareToPriorBest` in a domain module with typed reasons; persistence adapters perform owner-scoped bounded queries; application service composes a stable read model; thin routes validate/authenticate/call service/map `{code,message}` errors. No React, DB or AI in pure rules. Existing `Metric<T>` wraps computed displayed values with `atlas_computed`, while captured inputs remain `user_input`. The source set and rule version must be auditable.

**Read DTO:** `ProgressionObservation` contains raw reps/`weightKg`, all semantic columns or `unknown`, source set/workout IDs, `endedAt`, Córdoba `localDate`, provenance and capture version. `EligibilityResult` uses the §9b union. `WorkoutRepresentative` contains the selected source set and canonical cohort key. `ExerciseProgressionSummary` contains `readStatus: no_history|history_without_semantics|no_comparable_set|ready`, `currentRepresentative`, `previousComparableRepresentative`, `currentBest`, `comparison: baseline|new_pr|ties_best|below_best|null`, typed reason(s), metric ID `same_reps_external_load`, `progressionRuleVersion=1`, source IDs and provenance. For the requested cohort, `currentRepresentative` is selected from the **latest eligible closed workout by `(endedAt, workoutId)`**, after selecting the maximum eligible set within each workout. `previousComparableRepresentative` is from the latest earlier eligible closed workout in that same cohort. `currentBest` is the exact all-time eligible best in the cohort; PR classification compares current against the exact **best before that selected current workout**, not merely the latest previous representative. One eligible workout yields `baseline`. Unknown/absent values are `null`, not zero.

**API choice:** new authenticated `GET /api/exercises/[id]/progression?reps&amountBasis&side&limit&cursor` with exact exercise ownership, bounded history and the DTO above. `reps`, `amountBasis` and `side` select the cohort; `loadMode=external` and `purpose=working` are fixed by metric ID. There is **no candidate workout parameter** in v0.12: the service picks the latest eligible closed workout in that cohort as `currentRepresentative`, independently of `limit/cursor`; a still-open workout is only provisional raw context and never gets a PR result. `POST/PATCH /api/workouts/[id]/sets` accept the complete semantic tuple with capture version 1 and reject partial tuples. The existing `/api/stats/exercise/[id]/history` remains a bounded **raw** compatibility surface without PR claims. `/api/stats/prs` is retired per §13a; there is one user-facing PR definition. The new endpoint supplies the only PR result; no legacy route is allowed to call a new result “PR” while interpreting bare kg. HTTP errors remain typed `{code,message}`; a retired endpoint returns 410 with `PR_CONTRACT_RETIRED` once its caller has been removed.

### 14a. Low-friction, explicit write and read UX

On the **first set of an exercise in a workout**, show compact chips/selects for `loadMode`, `amountBasis` (hidden with visible “sin carga externa” for bodyweight), `side`, and `purpose`, beside reps and a mode-labeled amount field. When `side=alternating`, show a required, visible `repCountBasis=total|per_side` selector and explain what the entered reps count; hide/clear it for other sides. No value comes from exercise name, equipment, routine, last historical set or a hidden default. Saving is disabled until all required selections have been visibly chosen; the save summary repeats the selected semantics including rep basis when applicable. This is one short confirmation, not a large form on every set. For the **next set of the same exercise in the same workout**, prefill a local exercise/session draft from the **last explicitly confirmed** set, keep its chips visible/editable beside the amount, and persist the full tuple again when Save is pressed. The conditional rep basis is inherited visibly only for alternating. If mode/side changes, clear incompatible basis/amount/rep-basis choices and revalidate before enabling Save. Reload may restore only a previously saved explicit tuple from the same workout, visibly marked “reutilizado de la serie anterior”; it is still reviewed on save. No hidden default may make a PR-eligible row.

Legacy rows show reps and original number with “carga registrada; tipo no indicado”. They remain permanently raw/unknown: no edit or save may add v1 semantics to an existing legacy set. An open legacy row can receive only its existing nonsemantic edits (reps/recorded amount/index/exercise under current ownership rules) and retains all six semantic columns NULL; a closed row stays frozen apart from existing soft-delete behavior. If the user wants an explicitly declared performance, they create a **new v1 set** while a workout is active; no historical row is converted in v0.12. Bodyweight shows “peso corporal, sin carga externa” rather than “0 kg levantados”; assisted shows “asistencia: X kg” and never an upward-strength claim; per-side shows “X kg por lado”. Loading, empty, unknown and error states are distinct. Read surfaces display eligibility/reason copy from codes, source workout/date and metric name; they never stringify a bare `weightKg` as total resistance.

Telegram must also capture explicit facts. For v0.12 a compact `/log` or `/entreno` syntax includes named `mode`, `basis` (omitted only for bodyweight), `side`, `purpose`, and `repBasis` for alternating; parser/help show a concrete example. The old three-argument syntax responds with the new usage and **does not write**. A future conversational confirmation can reduce typing, but must require visible user confirmation before persistence; it cannot silently reuse an exercise-name default. `/resumen` uses mode-aware/unknown labels. This is a scoped capture-contract change, not a redesign of Telegram.

### 14b. Test and compatibility gates

Pure table tests cover every §9a row/catch-all, decimal normalization and exact ordering (including `1.1` versus `1.01` and variable-length fractions), zero sentinel, left/right separation, bilateral total versus per-side, assisted direction, warm-up, alternating rep basis, unknown/corrupt rows and mixed capture-version compatibility. Service tests cover owner isolation, deleted/open/incomplete rows, exact `exerciseId`, baseline/tie/strict greater, two sets in one workout, same `endedAt` tie by workout ID, and recomputation after deletion. API/contract tests cover typed reasons, bounded cursor **independent of all-time PR**, 410 retirement, old-client rejection, nonsemantic legacy edit retaining all NULL fields, no false PR on open workout, and DTO provenance. UI/e2e tests cover first-set explicit selection, conditional alternating rep basis, visible inherited draft and edit, bodyweight zero, assisted and legacy labels, old badge removal, and Telegram command/summary. `EXPLAIN QUERY PLAN` tests must show indexed cohort aggregate and bounded history access under a large multi-user fixture; CI lint, strict typecheck, Jest and Playwright Must remain the implementation gates. This discovery edits no code and runs no product tests.

## 15. UX surfaces enabled by the foundation

Safe first outputs: exact raw prior session (“última sesión registrada”), representative set from the last comparable closed workout, and best eligible set **with metric name and source**; a narrowly labeled same-reps external-load PR only after the semantic writer/read path and all old `weightKg` claims are reconciled. Show empty/unknown/loading/error separately. A per-exercise card can link to source workout and explain “sin comparación válida” when fields differ. Historical values may be shown verbatim with mode/unknown labels and without trend/PR language. v0.12 suppresses the current aggregate “strength” chart, volume cards and close-summary max-weight delta because mixed modes and bases make them unsafe; session counts/duration/streak remain. Future charts can plot one compatible cohort at a time; do not connect mixed exercises, reps, sides or modes with a line. Future milestones/celebrations may consume only validated `new_pr` results. A future body map needs a vetted exercise-to-muscle mapping plus an explicitly defined aggregate; the current `muscleGroup` string is not a physiological score.

**v0.13 bridge:** `raw set → semantic observation → eligibility → compatible cohort → progression result → stable, versioned read model | v0.13 presentation layer`. v0.12 exposes metric ID, rule version, provenance, source IDs, local display date, result/reasons and empty/unknown states. v0.13 can explore charts, PR visualization, milestone events, motion, celebrations, body-map inputs and a distinct visual language **through that DTO**, without querying or reinterpreting `workout_sets`. Body Map still requires its own anatomy and aggregation contract; no muscle score is implied by the v0.12 DTO. v0.13 remains separate design/motion/engagement discovery, not a hidden part of this implementation.

## 16. Future design, motion and engagement direction — separate wave

The product can become more distinctive through a coherent icon set, original movement illustrations, clearer hierarchy, useful feedback after a verified record, and purposeful motion. First conduct an icon/illustration audit: current generic/uneven symbols should be evaluated for semantic clarity at mobile size, contrast and accessibility; choose a custom visual language only after comparing production screens, then prototype rather than replacing all icons at once. Motion should mark state changes (set saved, comparison available, validated PR) with restrained timing and reduced-motion equivalents. A celebration must be triggered by a verifiable event, not by a first baseline or ambiguous legacy record.

`framer-motion`/current **Motion for React** is a plausible later fit for React microinteractions; [official docs](https://motion.dev/docs/react) confirm the maintained React API. Evaluate bundle/performance, SSR behavior and `prefers-reduced-motion` in a small prototype before adoption. **Three.js** belongs only in a later body-map discovery if 2D SVG cannot meet an agreed interaction need; its [WebGL renderer](https://threejs.org/docs/pages/WebGLRenderer.html) introduces graphics capability/performance considerations. `img2threejs` is not validated as an Atlas dependency or product requirement; research its actual tool/licensing/output quality separately before proposing it. Neither library belongs in v0.12 foundation.

Sequence: truthful set capture → comparable per-exercise read model → accessible, clear 2D progress visualization → event-based celebratory feedback → body-map research and optional 3D prototype → engagement experiment. Separate future discoveries: visual identity/iconography, motion/microinteraction language, body-map anatomy and metric semantics, and motivation/quest mechanics. Each needs its own user problem, success measure and accessibility guardrail.

## 22. Independent review findings and resolution

First independent verdict: **BLOCK**. The reviewer found three contract gaps: alternating sets could have compared identical rep numbers with different rep-count bases; the draft treated `setIndex` as though it timestamped a set's performance inside a workout; and mode-specific zero-load validation was left undecided. The reviewer also flagged “immutable observations” as inaccurate because open-workout sets remain editable.

Document-only resolution: alternating is excluded from the MVP comparison/PR and a future rep-basis key is required (§§9–11); PR classification now belongs to a closed workout representative compared with earlier closed workouts, using `setIndex` only for deterministic source tie selection (§§6, 11–12); zero is allowed only for plain bodyweight and the mode-aware validator requirement is explicit (§8); persisted observations are described as mutable while open (§6). A second pass caught residual wording that still described a set-level baseline or an intra-workout moment; §§5–6, 14–15 and 21 were aligned with the closed-workout model. **Prior discovery final review: APPROVE.** That was approval of the first artifact's internal consistency, before the owner decisions in this addendum.

**Fresh review of this decision addendum — FIRST verdict: BLOCK.** Four findings: a v1-only SQLite CHECK would contradict future compatible capture versions; alternating capture lacked the required visible rep-basis input; allowing an old row to acquire semantics contradicted permanent raw/unknown legacy history; and a limited history page could not supply an exact all-time PR. Document-only resolutions are recorded in §§9b, 13–14b: version-neutral DB tuple CHECK with v1-only service, conditional rep-basis UI, permanent NULL semantics for legacy rows, and separate exact indexed aggregate with a query-plan gate. Re-review then found one API ambiguity: “current” had no candidate workout parameter or selection rule. §14 now chooses the latest eligible closed workout by `(endedAt, workoutId)` within the requested cohort, independently of pagination, and defines previous/best-before relative to it. **Fresh final independent verdict: APPROVE.** The reviewer treated exact-aggregate index feasibility as the explicit implementation/query-plan gate in §13, not an unresolved product contract.
